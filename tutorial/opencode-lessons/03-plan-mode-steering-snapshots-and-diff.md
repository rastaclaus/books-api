# Урок 03. Plan-режим, steering на ходу, `/btw`, снапшоты `/undo` и ревью в `/diff`

## Цель урока

- Освоить два встроенных первичных агента — **Plan** и **Build** — и ввести в обиход главную практику безопасной разработки с агентом: *сначала план без правок файлов, потом реализация по утверждённому плану*.

## Теория-минимум: Plan, Steering и снапшоты

### Встроенные агенты Plan и Build

OpenCode V2 включает четыре видимых агента: **Build** (основной кодинг-агент, по умолчанию), **Plan** (исследует и планирует, не редактируя обычные файлы проекта), **General** и **Explore** (сабагенты). Переключение:

- `Shift+Tab` (`agent.cycle`) — цикл по первичным агентам;
- `Ctrl+X`, затем `A` (`/agents`) — полный список.

Ключевая особенность Plan-агента:

- он **не редактирует рабочие файлы проекта** — никакого `write`/`edit` в репозитории;
- он **может писать только файлы плана в `~/.opencode/plan`** — но исключительно когда вы его об этом попросите;
- он может **задавать вам вопросы** встроенным инструментом `question`: агент приостановит работу и покажет интерактивный диалог с вариантами ответов, чтобы уточнить требования до начала реализации.

Это делает Plan-режим идеальным местом для проектирования доменных моделей: агент исследует код, спорит с вами о деталях через вопросы, а рабочий код остаётся нетронутым.

### Todo-трекер

По умолчанию у агента нет тулов ведения списка задач. Включите в `opencode.jsonc`:

```jsonc
{
  "experimental": {
    "todo": true
  }
}
```

Агент получает инструмент `todowrite`: он ведёт карточку многошаговой работы (список задач со статусами pending/in_progress/completed). Посмотреть карточку в TUI можно командой `/todos`. Экспериментальная настройка — флаг может меняться между версиями, поэтому и живёт под ключом `experimental`.

### Управление работающим агентом

| Механизм | Как | Что делает |
|---|---|---|
| **Steering** | `Enter` во время генерации | Направляет текущий ход: ваш текст добавляется в контекст активного шага, агент учитывает его, не прерывая работу |
| **Queue** | `Ctrl+X`, затем `Enter` (`prompt.queue`) | Ставит промпт в очередь: он будет отправлен агенту после завершения текущего хода |
| Управление очередью | `<leader>q` (`session.queued_prompts`) | Диалог управления отложенными промптами (удаление — `Ctrl+D`, отмена постановки в очередь — `Ctrl+U`) |
| Фоновый режим | `Ctrl+B` (`session.background`) | Переводит блокирующий shell-тул агента (например, долгую команду) в фон, сессия продолжает работу; завершение придёт уведомлением |

Правило выбора: если уточнение должно повлиять на *текущий* ход — Steering через `Enter`. Если это отдельная задача «на потом» — Queue.

### Боковые вопросы `/btw`

`/btw <вопрос>` — задать вопрос о ходе разговора, не влияя на диалог. Ответ использует контекст сессии и текущую модель, но **не добавляется в историю диалога**: он открывается в отдельном диалоге (`C` — скопировать) и не влияет на последующие промпты. Идеально для «а что имелось в виду...» без замусоривания контекста. Пока `/btw` выполняется, в футере промпта виден его индикатор.

### Снапшоты: `/undo` и `/redo`

OpenCode делает снимки файлов для каждого шага модели (непосредственно перед вызовом модели и на его завершении) и помнит, какие пути изменились.

- `/undo` (`<leader>u`) — откатывает последнее сообщение пользователя **вместе с последовавшими изменениями файлов**, а сам промпт возвращается в композер для правки. Отправка отредактированного промпта завершает staged-rollback; отправка нового промпта подтверждает откат.
- `/redo` (`<leader>r`) — отменяет staged-rollback и возвращает состояние «до `/undo`», но только до отправки нового промпта.
- Откатить можно и не последнее сообщение: выберите нужное сообщение и действие **Revert**.

**Ограничения снапшотов** (важно держать в голове):

- требуется **Git-репозиторий** (вне Git `/undo` откатит только историю диалога, но не файлы);
- захватываются файлы **в активной директории сессии** внутри её Git-worktree;
- untracked-файлы захватываются только до **2 MiB** каждый, git-ignored файлы — никогда;
- снапшоты **не отменяют побочные эффекты shell-команд**: коммиты, процессы, записи в БД, изменения вне активной директории;
- снапшоты хранятся в отдельной внутренней Git-объектной базе в data-каталоге OpenCode и не создают коммитов в вашем репозитории.

Снапшоты — удобство, а не бэкап: важное коммитьте Git'ом.

### Diff Viewer `/diff`

`/diff` открывает ревью изменённых файлов:

- `d` (`diff.switch_source`) — переключение scope: **All**, **Committed**, **Uncommitted** (working) и **Last turn** (внутри сессии), либо выбор ветки сравнения **Base**;
- `v` (`diff.toggle_view`) — переключение split/unified вида;
- `m` (`diff.mark_reviewed`) — пометить файл просмотренным (и снять пометку);
- `n`/`p` (`alt+down`/`alt+up`) — навигация по файлам;
- `f` — полный экран; `?` — остальные шорткаты.

Выбор scope внутри `/diff` действует до выхода из TUI и не меняет `cli.json`. Начальный scope задаётся `"diffs": {"source": ...}` в `cli.json` (`branch` по умолчанию).

## Практика шаг за шагом

### Шаг 1. Включите todo-трекер

Дополните `opencode.jsonc` экспериментальной настройкой (конфиг подхватится горячей перезагрузкой):

```text
Добавь в opencode.jsonc экспериментальную опцию "experimental": {"todo": true} — агент получит тул todowrite для ведения списка задач в многошаговой работе. Остальное содержимое конфига не трогай.
```

Во втором терминале проверьте:

```bash
opencode debug config | grep -A3 experimental
```

### Шаг 2. Спроектируйте агрегат в Plan-режиме

Если вы сейчас в `build` — переключитесь: `Shift+Tab` (или `Ctrl+X`, затем `A`). Убедитесь, что активный агент — `plan`. Затем отправьте:

```text
Спроектируй ядро домена books-api: сущность Author, Value Object BookAsset и агрегат Book. Роль контекста — каталог свободной раздачи электронных книг (в открытом достоянии и под свободными лицензиями Creative Commons), только чистый Domain Layer на Python 3.14. Соблюдай AGENTS.md и docs/guidelines/domain-style.md.

Требования:
1. Author — Entity с идентификатором id: str и полным именем full_name: str (непустое после strip-нормализации).
2. BookAsset — Value Object (@dataclass(frozen=True, slots=True)): format: BookFormat, size_bytes: int (положительное), checksum: str (непустой).
3. Book — Aggregate Root со статусным перечислением BookStatus: DRAFT, PUBLISHED, WITHDRAWN.
   - Поля: id, title (непустая строка), language (LanguageCode), license (LicenseType), isbn: ISBN | None, authors (кортеж Author, минимум один), assets (кортеж BookAsset), status.
   - Создание только в статусе DRAFT: минимум один автор, непустое название, LanguageCode и свободный LicenseType; ISBN опционален.
   - add_asset(asset: BookAsset): не более одного ассета на каждый BookFormat; при статусе WITHDRAWN любые изменения запрещены (InvalidBookStateError).
   - publish(): только из DRAFT и только если есть хотя бы один BookAsset, иначе InvalidBookStateError; переводит в PUBLISHED.
   - withdraw(reason: str): причина обязана быть непустой строкой, иначе ValidationError; переводит в PUBLISHED в WITHDRAWN; повторный publish после withdraw запрещён (publish только из DRAFT).
   - Нарушения переходов и инвариантов — InvalidBookStateError (или ValidationError там, где это валидация входа), всё наследуется от DomainError.

Прежде чем дать финальный план, задай мне вопросы через тул question по любым двусмысленным местам (например, поведение при withdraw в статусе DRAFT, нужно ли хранить причину отзыва как поле).
По итогам дай план: список файлов, структура классов, список инвариантов и план тестов. Файлы проекта пока не меняй.
```

Пока Plan-агент исследует код, попробуйте steering: во время генерации напишите в композер уточнение и нажмите `Enter`:

```text
Мнение: хранить причину отзыва как поле withdrawn_reason: str в WITHDRAWN-состоянии — учти это в плане.
```

Агент не прервётся — он учтёт уточнение в текущем ходе. Если уточнение лучше отложить «на потом», используйте Queue: `Ctrl+X`, затем `Enter` (управление очередью — `<leader>q`).

Когда план готов, проверьте, что рабочие файлы нетронуты (Plan-агент не редактирует проект):

```text
!git status --short
```

Вывод должен быть пустым (или без новых файлов в `src/` и `tests/`). Это ключевой контракт Plan-режима.

> Совет: если план нужен как артефакт — попросите Plan-агента «запиши план в файл плана» (он умеет писать в `~/.opencode/plan`, но только по вашей просьбе).

### Шаг 3. Переключитесь в Build и реализуйте по плану

`Shift+Tab` — вернитесь в `build`. Отправьте:

```text
Реализуй агрегат по утверждённому плану:
1. src/books_api/domain/book.py: BookStatus (StrEnum), Author, BookAsset, Book — строго по плану и по правилам docs/guidelines/domain-style.md (frozen VO, валидация в __post_init__, нормализация через object.__setattr__, именованные константы порогов, никаких фабрик ради фабрик).
2. Экспортируй BookStatus, Author, BookAsset, Book в src/books_api/domain/__init__.py с обновлением __all__.
3. tests/test_book.py: создание в DRAFT (happy-path), запрет пустого названия/списка авторов/несвободной лицензии, add_asset с дубликатом формата и в WITHDRAWN, publish из DRAFT с ассетами и без них, withdraw с пустой и непустой причиной, повторный publish после withdraw.
Перед завершением прогони just check и just test.
```

В транскрипте вы увидите `todowrite`-карточку: агент будет отмечать шаги по мере выполнения (напомним: работает после включения `"experimental": {"todo": true}` из Шага 1). Открыть её можно и в TUI: `/todos`.

### Шаг 4. Steering во время реализации: добавьте два публичных члена агрегата

Пока Build-агент пишет код, не ждите паузы — направьте ход на ходу. Наберите в композере и нажмите `Enter` (Steering):

```text
Ещё добавь в Book метод available_formats() -> frozenset[BookFormat] (форматы уже добавленных ассетов) и свойство is_downloadable: bool (True только в статусе PUBLISHED). Покрой оба юнит-тестами и включи в план задач через todowrite.
```

Если хотите отправить это как задачу «после текущего шага», используйте Queue: `Ctrl+X`, затем `Enter` — промпт уйдёт в очередь; `<leader>q` покажет очередь с возможностью редактирования.

### Шаг 5. Боковой вопрос через `/btw`

Дождитесь завершения шага (или задайте вопрос параллельно — `/btw` работает и во время работы агента, индикатор виден в футере):

```text
/btw Почему в DDD сравнение сущностей (Author, Book) принято делать по идентификатору (__eq__/__hash__ по id), а Value Objects — по всем полям? Как это корректно оформить в Python для наших классов?
```

Ответ откроется в диалоге (нажмите `C`, чтобы скопировать) и **не попадёт в диалог с агентом**: контекст сессии останется чистым. Если вывод `/btw` покажется вам важным — попросите агента отдельно: «Учти правило идентичности DDD-сущностей и VO и примени его к Author».

### Шаг 6. Безопасный эксперимент с `/undo`

Проверим снапшоты на практике. Сначала попросите агента сделать маленькую лишнюю правку:

```text
Добавь в агрегат Book поле annotation: str | None = None — краткое описание книги, и обнови тесты.
```

Дождитесь окончания и посмотрите diff:

```text
!git diff --stat
```

Теперь откатите этот ход целиком — наберите:

```text
/undo
```

или нажмите `Ctrl+X`, затем `U` (`<leader>u`). Произойдут две вещи:

1. файлы вернутся к состоянию до этого шага (проверьте `!git diff --stat` — правки по `annotation` исчезли);
2. **промпт вернётся в композер для правки**.

Отредактируйте промпт в композере — замените его на другое указание:

```text
Вместо поля annotation добавь в Book метод summary(max_chars: int) -> str: обрезанное многоточием представление "title — first author" с длиной не более max_chars (именованная константа для дефолта в стиле domain-style.md), и тесты на обрезку.
```

Отправьте отредактированный промпт — снапшот-откат зафиксируется, и агент начнёт работу с новым заданием.

> Если передумали и хотите вернуть состояние «до `/undo`» — `/redo` (`Ctrl+X`, затем `R`, `<leader>r`) работает до отправки нового промпта.

Помните ограничения: если бы агент во время откатываемого шага, скажем, создал коммит или запустил процесс — снапшот это **не** отменил бы (побочные эффекты shell не откатываются).

### Шаг 7. Ревью в `/diff` и коммит

Когда реализация завершена, откройте Diff Viewer:

```text
/diff
```

В ревью:

- нажмите `d` — выберите scope **Last turn** (файлы, изменённые в последнем ходе сессии); для общего сравнения с веткой верните **All**;
- `v` — переключите split/unified вид, выберите удобный;
- листайте файлы `n`/`p`, и пройдясь по файлу, пометьте его просмотренным клавишей `m`;
- `f` — полный экран, `?` — другие шорткаты.

Затем сверните ревью (`Esc`) и проверьте масштаб изменений в терминале:

```bash
git diff --stat
just check
just test
```

Зафиксируйте этап коммитом — руками (наша `/commit` появится в Уроке 05):

```text
Проанализируй git status и git diff и создай осмысленный коммит в стиле Conventional Commits: src/books_api/domain/book.py, обновлённый src/books_api/domain/__init__.py и tests/test_book.py.
```

```bash
opencode debug config | grep -A3 experimental
just check && just test
uv run python -c "
from books_api.domain import Book, BookAsset, Author, BookFormat, LicenseType, LanguageCode
b = Book.create_test() if hasattr(Book, 'create_test') else None
print('imports ok')
"
git log -n 2 --oneline
```

Чеклист результата:

- [ ] В `opencode.jsonc` включён `"experimental": {"todo": true}`, и в транскрипте вы видели карточку задач (`todowrite`), а `/todos` открывает её в TUI.
- [ ] Вы спроектировали агрегат в Plan-агенте и убедились через `!git status --short`, что рабочие файлы не были изменены; Plan-агент задавал вопросы через тул `question` (или вы убедились, что он умеет).
- [ ] Вы направляли работающего агента через Enter-Steering (метод `available_formats()` и свойство `is_downloadable` появились в `Book` без прерывания хода) и/or ставили промпт в очередь (`Ctrl+X` → `Enter`, `<leader>q`).
- [ ] `/btw` дал ответ на вопрос про идентичность DDD-сущностей в отдельном диалоге, и ответ не попал в историю диалога.
- [ ] Эксперимент с `/undo` сработал: файлы вернулись к состоянию до шага, промпт вернулся в композер, вы отредактировали его и отправили новое указание (`summary(max_chars)` вместо `annotation`); `/redo` вы понимаете как отмену staged-rollback до отправки нового промпта.
- [ ] В `/diff` вы переключали scope клавишей `d` (Last turn / All), меняли вид клавишей `v` и помечали файлы клавишей `m`.
- [ ] `src/books_api/domain/book.py` содержит `BookStatus` (DRAFT/PUBLISHED/WITHDRAWN), `Author`, `BookAsset`, агрегат `Book` с инвариантами жизненного цикла; `just check` и `just test` зелёные; изменения закоммичены.

## Шпаргалка урока

| Действие | Клавиши / Команда | Назначение |
|---|---|---|
| Переключение первичных агентов | `Shift+Tab` / `Ctrl+X`+`A` (`/agents`) | Plan ↔ Build (Plan не редактирует файлы проекта) |
| Вопрос агента пользователю | тул `question` | Интерактивный диалог с вариантами (план-агент уточняет требования) |
| Todo-трекер | `"experimental": {"todo": true}` → тул `todowrite`, просмотр `/todos` | Карточка многошаговой работы |
| Steering | `Enter` во время генерации | Направление текущего хода без прерывания |
| Queue | `Ctrl+X` → `Enter` (`prompt.queue`), `<leader>q` | Отложенный промпт и управление очередью |
| Фоновый перевод тулов | `Ctrl+B` (`session.background`) | Долгая shell-команда уходит в фон, сессия продолжается |
| Боковой вопрос | `/btw <вопрос>` | Ответ в отдельном диалоге, в контекст диалога не попадает |
| Откат сообщения и файлов | `/undo` (`<leader>u`) | Откат + промпт возвращается в композер для правки |
| Возврат отката | `/redo` (`<leader>r`) | Отменяет staged-rollback (до отправки нового промпта) |
| Ревью изменений | `/diff` | `d` — scope (turn/working/committed/branch, Base), `v` — split/unified, `m` — пометка файла, `n`/`p` — навигация, `f` — полный экран, `?` — помощь |
| Снапшоты в конфиге | `"snapshots": false` | Отключение захвата файлов (по умолчанию включены) |
