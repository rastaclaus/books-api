# Урок 05. Кастомные slash-команды и shell-инъекции `` !`...` ``

[← Урок 04. Сессии, compaction, вложенные AGENTS.md и references](04-sessions-compaction-nested-instructions-and-references.md) | [Карта курса](README.md) | [Урок 06. Проектные скиллы со справочниками и скриптами →](06-project-skills-and-bundled-resources.md)

## Цель урока

- Освоить **пользовательские slash-команды**: файл `.opencode/commands/<имя>.md` превращает шаблон промпта в команду `/имя` (глобальные команды живут в `~/.config/opencode/commands/`, вложенные пути дают вложенные неймспейсы — `.opencode/commands/qa/check.md` становится `/qa/check`).
- Научиться параметризовать команды: frontmatter (`description`, `agent`, `model` в формате `provider/model#variant`, `subagent: true` для запуска в фоновой дочерней сессии; устаревшее поле `subtask` в V2 не используем) и шаблонизация аргументов (`$ARGUMENTS` — вся строка, `$1`/`$2` — позиционные, кавычки группируют слова).
- Освоить **shell-инъекции**: блок `` !`команда` `` в шаблоне выполняется в рабочей директории проекта **до отправки** промпта, а его вывод вставляется в сообщение.
- Собрать рабочий инструментарий проекта: `/commit` (атомарный коммит со сбором состояния git и прогоном проверок), `/check-module` (точечная проверка модуля) и `/explain-error` (разбор ошибки в read-only режиме через агента `plan`).

## Теория-минимум: как работают кастомные команды

### Файлы команд

Только файлы `.md` обнаруживаются автоматически:

| Расположение | Область действия |
|---|---|
| `.opencode/commands/<имя>.md` | Команда уровня проекта, коммитится в Git и доступна всей команде |
| `~/.config/opencode/commands/<имя>.md` | Глобальная команда пользователя, доступна во всех проектах |
| `.opencode/commands/<dir>/<имя>.md` | Вложенный неймспейс: `qa/check.md` → вызов `/qa/check` |

Тело `.md` (за вычетом frontmatter) — это шаблон промпта: при вызове `/review src/auth.ts` OpenCode отправит модели развёрнутый текст как обычное сообщение пользователя.

### Frontmatter

```markdown
---
description: Проверка кода на корректность
agent: plan
model: provider/model#high
subagent: true
---

Проверь $ARGUMENTS. Сначала опиши баги.
```

| Поле | Обязательное | Поведение |
|---|---|---|
| `description` | нет | Показывается в списках команд и при поиске |
| `agent` | нет | Агент, выбранный на время выполнения команды |
| `model` | нет | Переопределение модели: `provider/model` или `provider/model#variant` |
| `subagent` | нет | `true` — запуск в фоновой дочерней сессии (родительская остаётся свободной, результат вернётся в неё); `false` — форсировать текущую сессию |

> **Важно для V2:** поле `subtask` — устаревший алиас `subagent`; в новых файлах не используйте его. `template` в Markdown-frontmatter класть нельзя — тело файла и есть шаблон.

### Шаблонизация аргументов

- **`$ARGUMENTS`** — вся строка аргументов ровно как введена: для `/component Account Settings` подставится `Account Settings`.
- **`$1`, `$2`, ...** — позиционные аргументы; одиночные или двойные кавычки группируют слова и сами удаляются. Для `/check src/auth.ts "error handling"`: `$1` → `src/auth.ts`, `$2` → `error handling`.
- Плейсхолдер с наибольшим номером поглощает свой аргумент и всё, что после него; пропущенные позиции становятся пустыми строками.
- Если в шаблоне нет ни `$ARGUMENTS`, ни позиционных плейсхолдеров, непустые аргументы дописываются после пустой строки в конец промпта.

### Shell-инъекции `` !`...` ``

Блок `` !`команда` `` в шаблоне выполняется настроенным shell'ом **в активной директории проекта до отправки промпта**, и его вывод вставляется в сообщение:

```markdown
Проверь этот дифф:

!`git diff --stat && git diff`
```

Плейсхолдеры аргументов раскрываются **раньше** shell-блоков — поэтому для `/history 5` команда `` !`git log --oneline -$1` `` получит `git log --oneline -5`. Отсюда правило безопасности: **не помещайте недоверенные аргументы внутрь shell-блоков** — их содержимое попадает прямо в shell.

Ещё две детали:

- `@путь` в сохранённом шаблоне **не** раскрывается в прикрепление — это обычный текст промпта; файлы прикрепляйте через композер при вызове команды.
- Команды можно объявлять и декларативно в `opencode.jsonc` — секция `commands` с обязательным полем `template`:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "commands": {
    "review": {
      "description": "Проверка кода на корректность",
      "template": "Проверь $ARGUMENTS. Сначала опиши баги.",
    },
  },
}
```

### Приоритет и hot-reload

Markdown- и JSON-команды живут в одном реестре. При совпадении имён **проектные команды переопределяют глобальные**, а более близкие проектные — команды из родительских каталогов; пользовательская команда может даже заменить встроенную. Файлы команд и конфиг перечитываются автоматически: сохранение `.md` обновляет команду без перезапуска OpenCode.

## Практика шаг за шагом

### Шаг 1. Команда `/commit`: атомарный коммит со сбором состояния

Создадим команду, которая сама собирает картину изменений (три shell-инъекции) и поручает агенту оформить коммит. Отправьте агенту промпт:

```text
Создай файл .opencode/commands/commit.md с frontmatter description: "Создать атомарный коммит в стиле Conventional Commits" и таким телом (тело должно начинаться с трёх shell-инъекций, каждая на отдельной строке-блоке):

Текущее состояние рабочей копии:
!`git status --short`

Сводка изменений:
!`git diff --stat`

Результат ворот качества:
!`just check && just test`

Далее текст задачи агенту: "Проанализируй вывод выше, сгруппируй изменения в ОДИН атомарный коммит в стиле Conventional Commits (тип + область в scope, императивное описание в строке темы), добавь краткое тело коммита с обоснованием и списком затронутых файлов. Не добавляй в коммит случайные и временные файлы. Если just check или just test упали — сначала исправь замечания и только потом коммить."

После создания файла вызови /commit и покажи, что команда появилась в списке слэш-команд.
```

Обратите внимание: shell-блоки выполняются **до** отправки промпта — агент сразу видит вывод `git status`, `git diff --stat` и результат проверок, не выполняя их сам.

### Шаг 2. Команда `/check-module`: позиционные аргументы

Теперь команда с двумя параметрами. Отправьте агенту:

```text
Создай файл .opencode/commands/check-module.md с frontmatter description: "Точечная проверка одного модуля" и таким телом:

---
description: Точечная проверка одного модуля
---

Выполни точечную проверку модуля $1. Фокус проверки: $2.

Шаги:
1. Прочитай файл $1 полностью и сверь его с правилами AGENTS.md и вложенными AGENTS.md его каталога.
2. Прогони точечно линтер и тайпчекер только по этому файлу и его тестам: uv run ruff check $1 && uv run ty check $1 (если на файл ругаются правила, не применимые к точечной проверке, объясни почему).
3. Найди тесты, покрывающие этот модуль (grep по имени модуля в tests/), и запусти только их: uv run pytest -q <путь к тестам>.
4. Отчитайся таблицей: | Проверка | Результат | Комментарий |, затем краткий вывод: что исправить в первую очередь с учётом фокуса проверки.
```

Протестируйте её на модуле из Урока 04, взяв второй аргумент в кавычки:

```text
/check-module src/books_api/domain/reader.py "граничные случаи квот"
```

В промпт подставится: `$1` → `src/books_api/domain/reader.py`, `$2` → `граничные случаи квот`. Агент проверит именно модуль и именно граничные случаи квот (0 у заблокированного, 3/25 лимиты, повторное скачивание).

### Шаг 3. Команда `/explain-error`: разбор без права правок

Для разбора ошибок полезен агент `plan` — он не редактирует файлы. Отправьте агенту:

```text
Создай файл .opencode/commands/explain-error.md с таким содержимым:

---
description: Разобрать ошибку или подозрительный код без правок
agent: plan
---

Разбери $ARGUMENTS: объясни причину ошибки или подозрительного поведения, задействованные символы и цепочку вызовов, предложи 2-3 варианта исправления с trade-offs. Файлы НЕ изменяй — только анализ.

Затем вызови /explain-error tests/test_reader.py::test_suspended_reader и покажи разбор.
```

При вызове сработает правило «нет плейсхолдера $ARGUMENTS/$1 — аргументы дописываются в конец» только частично: `$ARGUMENTS` здесь есть, так что идентификатор теста подставится в текст. Сессия переключится на агента `plan`, и любые правки будут ему недоступны.

### Шаг 4. Hot-reload: правка команды подхватывается сразу

Проверим, что команды перечитываются без перезапуска. Не выходя из сессии, добавьте в `.opencode/commands/check-module.md` одну строку в конец (в редакторе или во втором терминале):

```bash
printf '\nВ конце отчёта укажи затраченное число найденных тестов.\n' >> .opencode/commands/check-module.md
```

И сразу вызовите снова:

```text
/check-module src/books_api/domain/reader.py "повторное скачивание не расходует квоту"
```

Команда выполнится уже в новой редакции — с подсчётом тестов. Перезапуск OpenCode не потребовался.

> **Для справки:** ту же команду можно объявить в `opencode.jsonc` через `"commands": { "check-module": { "template": "..." } }` — реестр общий, и проектное объявление переопределит глобальный `.md` с тем же именем.

### Шаг 5. Первый атомарный коммит через `/commit`

Настал момент, ради которого создавалась `/commit`: урок добавил команду, модуль и файлы урока 04. Просто вызовите:

```text
/commit
```

Агент увидит собранные выводы `git status --short`, `git diff --stat` и зелёный результат `just check && just test`, сгруппирует изменения и создаст коммит в стиле Conventional Commits. Проверьте результат:

```bash
git log -n 1 --stat
```

## Самопроверка

Выполните в терминале (или через `!`-команду / второй терминал):

```bash
just check
just test
test -f .opencode/commands/commit.md && echo "/commit: ok"
test -f .opencode/commands/check-module.md && echo "/check-module: ok"
test -f .opencode/commands/explain-error.md && echo "/explain-error: ok"
git log -n 1 --format '%s'
```

Чеклист результата:

- [ ] `.opencode/commands/commit.md` содержит три shell-инъекции (`` !`git status --short` ``, `` !`git diff --stat` ``, `` !`just check && just test` ``) и инструкцию по атомарному коммиту; `/commit` создал коммит в стиле Conventional Commits с телом и списком файлов.
- [ ] `/check-module src/books_api/domain/reader.py "граничные случаи квот"` подставила `$1` и `$2` (в кавычках) корректно, и агент вернул отчёт таблицей по ruff/ty и связанным тестам.
- [ ] `/explain-error` запустилась с `agent: plan` во frontmatter — разбор без правок файлов.
- [ ] Вы убедились в hot-reload: правка `.md` подхватилась следующим вызовом команды без перезапуска OpenCode.
- [ ] Во всех шаблонах нет устаревшего поля `subtask` и нет `template` в Markdown-frontmatter.

## Шпаргалка урока

| Команда / Файл | Назначение |
|---|---|
| `.opencode/commands/<имя>.md` | Проектная slash-команда `/имя` (глобальные — в `~/.config/opencode/commands/`) |
| `.opencode/commands/qa/check.md` | Вложенный неймспейс: вызов как `/qa/check` |
| Frontmatter `description` / `agent` / `model` | Метаданные команды; `model` — `provider/model#variant` |
| Frontmatter `subagent: true` | Запуск в фоновой дочерней сессии (`subtask` — устаревший алиас, не использовать) |
| `$ARGUMENTS` / `$1`, `$2` | Вся строка аргументов / позиционные (кавычки группируют слова) |
| `` !`команда` `` | Shell-инъекция: выполняется до отправки промпта, вывод вставляется в сообщение (аргументы раскрываются раньше; недоверенные аргументы в shell-блоки не класть) |
| `"commands"` в `opencode.jsonc` | Декларативные JSON-команды с обязательным `template`; общий реестр с `.md` |
| Приоритет | Проектные команды переопределяют глобальные; hot-reload при сохранении файла |
| `/commit` · `/check-module` · `/explain-error` | Рабочие команды проекта, созданные в этом уроке |
