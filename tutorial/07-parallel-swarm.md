## Цель урока

- Понять архитектуру мультиагентного роя (**`Swarm`**) в `jcode`: роли координатора и воркеров, синхронизацию через именованные дорожки (`todo` lanes) и защиту от конфликтов при правке файлов.
- Настроить проектный файл маршрутизации и правил роя **`.jcode/swarm-prompt.md`** (и команду `/swarm-prompt`).
- Освоить наблюдение за параллельными агентами в реальном времени через `/observe`, `/splitview`, `/swarm` и выбор модели воркеров через `/subagent-model`.
- Параллельно двумя воркерами разработать два независимых модуля домена `books-api`: `DownloadService` (выдача грантов и доменных событий) и поиск по каталогу (`CatalogQuery` + `InMemoryBookRepository`).

## Теория-минимум: как Swarm работает в одном репозитории без хаоса

В отличие от тяжёлых CLI-агентов (где каждая новая сессия съедает сотни мегабайт RAM), дополнительная headless-сессия в `jcode` занимает около **3–4 МБ памяти** и управляется единым локальным сервером-демоном. Это позволяет запускать параллельных агентов прямо в одной рабочей директории без обязательного размножения git-worktree на каждый чих.

### Ключевые правила архитектуры Swarm в `jcode`

1. **Одноуровневое ветвление (Root-only spawning).** Спавнить воркеров может только корневая сессия (координатор, глубина `0`). Воркеры не могут бесконечно плодить суб-воркеров и отчитываются обратно родителю.
2. **Дорожка `todo` как единый источник правды.** Координатор разбивает фазу плана на параллельные именованные дорожки (`lanes`, например `download-service` и `catalog-search`). При спавне воркера (`owner: "worker"` или вызов `swarm(action="spawn", label="...")`) эта дорожка автоматически предзаполняется в список задач воркера и синхронизируется с координатором.
3. **Автоматические уведомления о параллельных правках.** Если воркер А изменил файл, который ранее читал воркер Б, сервер `jcode` автоматически уведомляет воркера Б о сдвиге кода под ногами, чтобы тот сверил diff и не затёр чужую работу.
4. **Автоматическая доставка итогов.** Когда воркер завершает порученный ход, демон сам пересылает сжатый хвост его отчёта координатору, а координатор интегрирует изменения, прогоняет общие `just check` и `just test` и гасит освободившихся воркеров (`swarm(action="stop")`).

### Проектная настройка `.jcode/swarm-prompt.md`

По аналогии с системным промптом, правила маршрутизации и координации роя можно задать на уровне проекта в файле **`./.jcode/swarm-prompt.md`** (он имеет приоритет над глобальным `~/.jcode/swarm-prompt.md`; пустой файл безопасно игнорируется). Посмотреть активный промпт или изменить его прямо из TUI позволяет команда `/swarm-prompt`, а выбрать модель для спавнящихся воркеров можно командой `/subagent-model` (или `/agents swarm <model>`).

## Практика шаг за шагом

### Шаг 1. Создайте проектный `.jcode/swarm-prompt.md`

Зададим чёткие границы для параллельных воркеров `books-api`, чтобы они не толкались локтями в `src/books_api/domain/__init__.py`. Создайте файл `.jcode/swarm-prompt.md`:

```markdown
# Правила координации Swarm в проекте books-api

- Разделяй параллельные задачи строго по отдельным файлам модулей и отдельным файлам тестов (`tests/test_<module>.py`).
- Каждый воркер перед отчётом проверяет свои файлы точечно (`uv run ruff check <файлы>`, `uv run ty check <файлы>`, `uv run pytest -q <тест>`), чтобы не мешать параллельной дорожке.
- Воркеры НЕ должны редактировать общий фасад `src/books_api/domain/__init__.py`: экспорт в `__init__.py` и финальный общий прогон `just check` и `just test` выполняет корневой координатор после завершения воркеров.
- Не создавай воркеров-ревьюеров или чистых разведчиков без собственной дорожки кода и тестов.
```

Проверьте в TUI, что настройка подхватилась:

```text
/swarm status
/swarm-prompt
/subagent-model
```

> При желании вы можете также включить режим `/effort swarm`, который автоматически добавляет к вашим запросам установку решать задачи параллельным роем.

### Шаг 2. Запустите параллельную разработку двух подсистем домена

Отправьте координатору задачу, которая естественно распадается на две независимые дорожки без пересечения файлов:

```text
Используй Swarm с двумя параллельными воркерами на отдельных дорожках todo-плана:

Дорожка 1 (`download-service`, файлы `src/books_api/domain/download.py` и `tests/test_download.py`):
- Неизменяемое доменное событие `BookDownloaded` (`book_id`, `reader_id`, `format: BookFormat`, `occurred_at: datetime`) и результат `DownloadGrant` (`book_id`, `reader_id`, `format`, `checksum`, `license_notice: str`, `event: BookDownloaded`, `quota_consumed: bool`).
- Доменный сервис `DownloadService` с методом `request_download(book: Book, reader: Reader, fmt: BookFormat, downloaded_today: Collection[str], now: datetime) -> DownloadGrant`:
  1) проверяет, что книга доступна для раздачи (`book.is_downloadable`), иначе `InvalidBookStateError`;
  2) проверяет наличие запрошенного формата `fmt` у книги;
  3) проверяет допуск и суточную квоту `reader` с учётом `downloaded_today` (повторное скачивание той же книги в те же сутки не тратит квоту), иначе `QuotaExceededError`;
  4) формирует `license_notice` через `build_license_notice(book)` и возвращает `DownloadGrant`.

Дорожка 2 (`catalog-search`, файлы `src/books_api/domain/catalog.py` и `tests/test_catalog.py`):
- Неизменяемый фильтр `CatalogQuery` (`text: str | None = None`, `language: LanguageCode | None = None`, `format: BookFormat | None = None`, `license: LicenseType | None = None`, `only_downloadable: bool = True`).
- Протокол `BookRepository` (`typing.Protocol`: `add(book: Book) -> None`, `get(book_id: str) -> Book | None`, `search(query: CatalogQuery) -> tuple[Book, ...]`).
- Эталонную чистую реализацию `InMemoryBookRepository`, выполняющую поиск без учёта регистра по названию книги и именам авторов + фильтрацию по языку, формату и лицензии.

Дождись обоих воркеров (`await_members`), интегрируй экспорты в `src/books_api/domain/__init__.py`, прогони общие `just check` и `just test` и останови завершивших работу воркеров.
```

### Шаг 3. Понаблюдайте за роем через `/observe` и `/splitview`

Пока воркеры параллельно пишут `download.py` и `catalog.py`, введите в TUI:

```text
/splitview
```

или:

```text
/observe
```

Вы увидите живую боковую панель с потоком мыслей и вызовов инструментов дочерних воркеров, а в виджете статуса роя будут меняться их состояния: `spawned` -> `ready` -> `running` -> `completed` -> `stopped`.

После того как координатор соберёт оба модуля, обновит `__init__.py` и подтвердит зелёные `just check` и `just test`, зафиксируйте результат:

```text
/commit
```

## Самопроверка

Проверьте в терминале:

```bash
ls -la src/books_api/domain/ tests/
just check
just test -v
```

Чеклист результата:

- [ ] Настроен `.jcode/swarm-prompt.md`, который виден через `/swarm-prompt`.
- [ ] Созданы оба модуля (`download.py` и `catalog.py`) и оба набора тестов (`test_download.py`, `test_catalog.py`) без конфликтов в `__init__.py`.
- [ ] Свободные воркеры аккуратно остановлены после интеграции, а полная проверка `just check` и `just test -v` проходит без ошибок.
