## Теория-минимум: `jcode` как программируемый CLI-компонент

Интерактивный TUI прекрасен для ежедневной разработки, но часто хочется встроить интеллект агента в обычный bash/Python-скрипт или CI-проверку (например, проверить архитектурные правила в PR, сгенерировать changelog или выгрузить структурированный отчёт в JSON).

### Рекомендуемые флаги для скриптов и обёрток

```bash
jcode --quiet --no-update --no-selfdev run ...
```

- `--quiet` убирает служебные сообщения статуса из вывода, оставляя `stderr` пустым при отсутствии ошибок.
- `--no-update` и `--no-selfdev` отключают фоновые проверки обновлений и автоопределение репозитория самого `jcode`.
- `--json` возвращает единый машиночитаемый JSON-объект в `stdout` (`session_id`, `provider`, `model`, `text`, `usage`).
- `--ndjson` стримит события хода построчно (`start`, `text_delta`, `tool_start`, `tool_done`, `tokens`, `done`) в реальном времени.

### Песочницы инструментов (`--tool-profile`, `--tools`, `--disabled-tools`)

Когда вы запускаете `jcode run` из автоматического скрипта, давать модели полный набор пишущих инструментов (`write`, `edit`, `bash`) не всегда безопасно. В `jcode` набор инструментов, видимых и доступных модели, можно урезать прямо при запуске:

| Флаг CLI | Что делает | Пример |
|---|---|---|
| `--tool-profile <full\|minimal\|none>` | Выбирает базовый профиль инструментов (`none` скрывает все тулы для чистого текстового ответа) | `jcode --quiet --tool-profile none run "Объясни SPDX CC-BY-SA"` |
| `--tools <список>` | Явный белый список разрешённых инструментов (например, строго только чтение и поиск по коду) | `jcode --quiet --tools read,agentgrep run "..."` |
| `--disabled-tools <список>` | Чёрный список инструментов, которые нужно скрыть из выбранного профиля | `jcode --quiet --disabled-tools bash,write,edit,apply_patch run "..."` |

Если инструмент не включён в `--tools`, он даже не регистрируется для модели: агент физически не сможет ни модифицировать файл, ни запустить произвольную команду в `bash`.

### Живые панели (`panel`)

Внутри интерактивной сессии (TUI и Desktop) агенту доступен инструмент **`panel`** (`action`: `spawn`, `update`, `focus`, `close`, `list`), который открывает отдельные вкладки-панели с живым рендерингом Markdown (включая `mermaid`-схемы) или PDF-документов, привязанные к файлу на диске или тексту. Закрытие панели никогда не удаляет исходный файл на диске, а при обновлении файла панель перечитывает актуальное содержимое.

## Практика шаг за шагом

### Шаг 1. Сгенерируйте карту архитектуры `books-api` и откройте её в живой панели

В интерактивной сессии `jcode` попросите агента проанализировать готовый пакет `src/books_api/domain/`, создать наглядную документацию с `mermaid`-диаграммой и сразу открыть её в панели:

```text
Изучи все модули `src/books_api/domain/` и создай файл `docs/domain-architecture.md` с краткой картой построенной доменной модели books-api:
1. Mermaid-диаграмма классов и взаимодействий (`Book`, `Author`, `BookAsset`, `Reader`, `LicenseType`, `DownloadService`, `CatalogQuery`, `BookRepository`).
2. Таблица всех ключевых бизнес-инвариантов и выбрасываемых подклассов `DomainError`.
3. Примеры использования публичного API домена в 15-20 строках Python-кода.

После записи файла открой `docs/domain-architecture.md` в боковой панели с заголовком "Books-API Domain Map" через инструмент `panel`.
```

Посмотрите, как `jcode` создаст `docs/domain-architecture.md` и вызовет `panel(action="spawn", file_path="docs/domain-architecture.md", title="Books-API Domain Map")`.

### Шаг 2. Запустите строго изолированный read-only аудит через `jcode run --tools`

Перейдите во второй терминал и выполните одноразовую проверку домена в жёсткой песочнице из двух read-only инструментов (`read` и `agentgrep`), получив структурированный JSON-ответ:

```bash
jcode --quiet --no-update --no-selfdev \
  --tools read,agentgrep \
  run --json \
  "Проверь пакет src/books_api/domain/: 1) нет ли внешних runtime-зависимостей вне стандартной библиотеки Python; 2) все ли публичные классы экспортированы в __all__. Ответь коротко: VERDICT: OK или VERDICT: FAIL и 3 пункта фактов."
```

Обратите внимание на красоту этого вызова:
- У агента есть быстрый кодовый поиск `agentgrep` и чтение файлов `read`, но **нет `bash`, `write`, `edit` и `apply_patch`**. Такой шаг можно смело ставить в любую автоматизацию.
- На выходе в `stdout` вы получили чистый JSON со статистикой токенов `usage` и полем `"text"`, который легко разобрать через `jq -r .text` или `python3 -c 'import sys, json; print(json.load(sys.stdin)["text"])'`.

### Шаг 3. Попробуйте потоковый режим `--ndjson` и скрипт проверки `scripts/ci_domain_audit.sh`

Создайте небольшой переиспользуемый скрипт `scripts/ci_domain_audit.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail

echo "1/2 Running unit tests via uv..."
uv run pytest -q

echo "2/2 Running read-only jcode architectural audit..."
verdict=$(
  jcode --quiet --no-update --no-selfdev \
    --tools read,agentgrep \
    run --json \
    "Verify that src/books_api/domain/ contains only pure Python domain code with zero web/DB imports and consistent DomainError subclasses. End your reply with exact line STATUS: PASS or STATUS: FAIL." \
  | python3 -c 'import json, sys; print(json.load(sys.stdin)["text"])'
)

printf "%s\n" "$verdict"
grep -q "STATUS: PASS" <<<"$verdict"
```

Сделайте скрипт исполняемым и запустите его:

```bash
chmod +x scripts/ci_domain_audit.sh
./scripts/ci_domain_audit.sh
```

Зафиксируйте финальные артефакты проекта в Git:

```text
/commit
```
